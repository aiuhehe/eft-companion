## 1. 目的

EFT コンパニオンを使っている仲間同士で、**各自の「出撃準備タブの目標」を Discord に持ち寄り、合算して表示する**。

- 出撃前に「**どのマップに行くと全員の目標が多く進むか**」を選ぶ
- 行き先が決まったら、そのマップで**重なっている目標**（同じアイテムの収集・同じ撃破対象・同じタスク）をまとめて見る
- 1日の長いプレイ（〜12時間）でも、遊んでいる間はボードが残り続ける

## 2. 段階

| 段階 | アプリ側 | Bot 側 |
|---|---|---|
| **1. 連携と送信** | 設定タブで Bot と連携し、目標の変化を自動送信する（「今すぐ送信」・送る内容の確認用の JSON 保存を含む）。マップ名の正規化（§4.4） | `/raid link`・連携 API・受信 API（§11） |
| **2. 出撃ボード** | 出撃準備タブに同期状態を表示 | `/raid start` でボードを投稿し、参加者の目標を合算して自動更新・6時間で終了（§6〜§9） |
| **3. 仲間のボード** | 出撃準備タブに仲間の目標をメンバー別の色で重ねて表示（§11.4） | 読み込み API・[地図で見る]・`/raid mapimage`（§6.3） |
| **4. ピンの共有** | マップタブのピンを Discord サーバーの仲間と共有する。誰でも追加・編集・削除できる（§11.5） | ピンの保存・読み込み API、メモ画像の保存（§11.5） |
| **今後** | 目標の途中進捗（#28） | 参加者アバターの合成画像・通話チャンネルとの連動（§13） |

## 3. 設計の要点

### 3.1 共有のしかた

| 項目 | 設計 |
|---|---|
| 共有の方式 | **トークン連携＋アプリからの自動送信（push）**。Bot からブラウザのデータを取りに行くことはできない（データは各自の localStorage にしかない）ため、送るのはアプリ側（§11） |
| 連携の手順 | **6桁コード（5分で失効）**が基本。GitHub Pages 版は「アプリの設定を開く」ボタンで設定タブを開ける（コードは手で入力する・§11.1） |
| 送信元の制限 | **しない**（`file://` の `null` も可）。認証はヘッダーの連携トークンで、Cookie を使わないため、送信元で絞らなくても安全性は落ちない（§11.3） |
| 共有データの範囲 | **全マップ分を一括**で送り、各目標に `maps[]` を持たせる。マップごとの振り分けは受け取った側で行う（§4） |
| データを作る関数 | `buildRaidShareData()`。自動送信・今すぐ送信・JSON 保存のどれでも同じ関数を使う |
| マップ名 | **揺らさない。** tarkov.dev のデータはそのまま受け取り、アプリ側で出撃準備タブのマップ一覧（`RAID_MAPS`）の名前に正規化する。表示にも共有データにも正規化後の名前だけを使う（§4.4） |
| 連携トークンとバックアップ | **全データバックアップに含めない。** トークンは解除するまで使えるため、バックアップファイルが人の手に渡ると、なりすまして送れてしまう。復元後は6桁コードで連携し直す |

### 3.2 出撃ボード

| 項目 | 設計 |
|---|---|
| ボードの寿命 | **最後の操作から6時間**で自動終了。`/raid end` で手動終了もできる（§9） |
| 最大人数 | **5人**（タルコフのパーティー上限）。6人目の [参加する] には「満員です」と本人にだけ返す |
| 参加者の特定 | ボードの **[参加する] / [抜ける] ボタン**。HTTP Interactions でも押した人が分かる（スタンプは Gateway 常駐が必要なため使わない） |
| 参加者の表示 | **メンバー別の色マーカー＋メンション**。並びは参加順（＝色の割り当て順） |
| 個数の表示 | 行にはタスクの必要数（例「ガス分析器 FIR ×2」）を出し、色マーカーの横に**各自の残り**（「🟥 あと2 🟩 あと1」）を出す。必要数がタスクごとに違う場合は行の数を省く |
| 撃破の数 | **合計しない。** キルはパーティーで共有されるので、各自の残りのうち一番多い数を倒せば全員が終わる（§8.1） |
| どのマップでもよい目標 | マップ表示の末尾「どのマップでもOK」にまとめる。最上部の「共通の目標」には入れず、重なりは ★ で示す |
| 同期時刻 | 参加者ごとに最終同期時刻を出す（古さで表示は変えない） |
| 残り個数の元データ | 出撃準備タブで未チェックの目標は、必要数をそのまま残りとする。目標ごとの途中進捗を記録できるようになったら（#28）、目標に `remaining` を付けて送る |
| 絵文字 | アプリ UI の絵文字禁止ルールは Discord 上の表示には適用しない（色マーカーに使う） |

### 3.3 仲間のボード・マップ画像

| 項目 | 設計 |
|---|---|
| 仲間のボード | **出撃準備タブの中**に置く（新しいタブは作らない）。自分の目標一覧に仲間の目標を重ね、誰の目標かを**メンバー別の色**（Discord のボードと同じ割り当て）で示す。データは Bot が仲介する（§11.4） |
| マップ画像 | **サーバーごとにメンバーが Discord からアップロード**する（`/raid mapimage`・§6.3）。画像の作者から使用の許可を得たうえで、そのサーバーの仲間内だけで使う |
| マップピン | **Discord サーバー単位で Bot（D1・R2）に持つ。** ピンは「どの目標がマップのどこにあるか」というゲーム内の事実で、人によって変わらないので、ブラウザごとに持たずサーバーの仲間全員で1セットを育てる。**サーバーのメンバーなら誰でも追加・編集・削除できる**（§11.5） |
| Discord Activity | **使わない。** 使うサーバーは25人以上で、未検証の Activity は25人未満のサーバーでしか起動できないため。詳細表示はアプリ内の仲間のボードで行う |

### 3.4 基盤

| 項目 | 設計 |
|---|---|
| ホスティング | **Cloudflare Workers（HTTP Interactions）＋ D1（データベース）＋ R2（マップ画像の保存）**（§5） |
| 常駐プロセス | 持たない。スタンプ・通話メンバーの取得・アバター画像の合成が必要になったときだけ、Gateway に接続する補助プログラムを追加する |

## 4. 共有データ形式 v1（アプリ ⇔ Bot の取り決め）

### 4.1 JSON

```json
{
  "v": 1,
  "app": "eft-tool",
  "mode": "pvp",
  "gameMode": "regular",
  "lang": "ja",
  "level": 23,
  "createdAt": "2026-11-10T12:34:56Z",
  "tasks": [
    {
      "id": "<taskId>",
      "name": "Debut",
      "trader": "Prapor",
      "custom": false,
      "objectives": [
        { "id": "<objectiveId>", "cat": "kill", "label": "Scav", "count": 5,
          "maps": ["Customs"], "done": false, "detail": "(head) <=50m" },
        { "id": "<objectiveId>", "cat": "bring", "label": "MP-133 12ga shotgun",
          "itemId": "<itemId>", "count": 2, "maps": [], "done": false }
      ]
    }
  ]
}
```

### 4.2 フィールド

| フィールド | 必須 | 内容 |
|---|---|---|
| `v` | ○ | 形式のバージョン。今は `1` |
| `app` | ○ | 固定値 `"eft-tool"` |
| `mode` | ○ | アプリのモード（`pvp` / `pve` / `season_N`）。シーズンの区別に使う |
| `gameMode` | ○ | 実際のデータの取得先（`regular` / `pve` / `pvp-season`）。ボードの振り分けに使う |
| `lang` | ○ | 表示名の言語（`ja` / `en` …） |
| `level` | ○ | プレイヤーレベル |
| `createdAt` | ○ | 作成日時（ISO 8601・UTC） |
| `tasks[]` | ○ | 進行中（ボード登録済み・未完了）のタスク。目標が1件も無いタスクは含めない |
| `tasks[].id` / `name` / `trader` | ○ | タスクID・表示名・トレーダー名 |
| `tasks[].custom` | ○ | カスタムタスク（アプリで手動登録したタスク）なら `true`。ID はアプリ内でしか通用しない |
| `objectives[].id` | ○ | 目標ID。API の目標は `obj.id`、ID の無いカスタムタスクの目標は `raidObjKey()`（アプリの目標チェック用キーと同じ作り方） |
| `objectives[].cat` | ○ | `bring`（持ち込み）/ `collect`（収集）/ `place`（設置）/ `kill`（撃破）/ `extract`（脱出）/ `locate`（調査）。アプリの出撃準備タブと同じ分類 |
| `objectives[].label` | ○ | 表示名（下表） |
| `objectives[].count` | ○ | 必要数（無ければ 1） |
| `objectives[].maps` | ○ | 対象マップ名の配列（§4.4 で正規化済み）。**空配列 = どのマップでもよい** |
| `objectives[].done` | ○ | 本人が出撃準備タブでチェック済みか |
| `objectives[].fir` | | FIR（レイド内で見つけたもの）が必要なら `true`（`false` の場合は書かない） |
| `objectives[].itemId` | | アイテム系の目標のアイテムID（合算のキー） |
| `objectives[].categoryName` | | アイテムではなくカテゴリ指定の目標のカテゴリ名 |
| `objectives[].questItem` | | クエストアイテムの目標なら `true` |
| `objectives[].desc` | | 目標の説明文（`label` と同じなら書かない） |
| `objectives[].detail` | | 撃破の部位・距離などの補足 |

値が無いキーは書き出さない（大きさを抑えるため）。

**`label` の決め方**

| cat | label |
|---|---|
| `bring` / `collect`（アイテム） | アイテム名。カテゴリ指定ならカテゴリ名 |
| `collect`（クエストアイテム） | クエストアイテム名 |
| `kill` | 対象（`obj.target`。例: Scav / PMC / ボス名） |
| `place` / `extract` / `locate` | 目標の説明文 |

### 4.3 含めないもの

スタッシュ・所持金・ジャーナル・ハイドアウト・トレーダーの状態など、**目標以外の個人データは一切含めない**。マップピンも含めない（ピンは人ごとの共有データではなく、サーバー単位で別に共有する。§11.5）。

### 4.4 マップ名

`maps[]` には、アプリの `RAID_MAPS` の名前に正規化したものだけを入れる（重複は除く）。

tarkov.dev のデータでは、同じマップの派生版が別のマップとして登録されており、目標によっては派生版だけが付いている（2026-11-10 時点の regular で約20件）。tarkov.dev のデータはそのまま受け取り、アプリ側で次のように変換する。

| tarkov.dev のマップ | 正規化後 |
|---|---|
| Night Factory・Infected Factory | `Factory` |
| Ground Zero 21+・Ground Zero（チュートリアル版） | `Ground Zero` |
| The Lab（暗い版）・Infected Lab | `The Lab` |

- 正規化は、出撃準備タブのマップでの絞り込みと共有データの作成で**同じ関数**を使う（実装済み・Issue #30: `normalizeRaidMapName` / `normalizeRaidMaps`・対応表 `RAID_MAP_ALIASES`・`00-constants.js`）。これにより、派生版だけが付いた目標も出撃準備タブに表示されるようになる。
- 取得したデータそのものは書き換えない（絞り込みと共有データ作成のときに正規化関数を通す）。
- `Icebreaker`・`The Labyrinth`・`Terminal` は派生版ではなく別のマップとして `RAID_MAPS` に加える。`RAID_MAPS` は次の13マップになる: Customs / Factory / Woods / Shoreline / Interchange / Reserve / Lighthouse / Streets of Tarkov / The Lab / Ground Zero / Icebreaker / The Labyrinth / Terminal。
- 「設置」以外でマップ指定が無い目標は「どのマップでもよい」扱い。「設置」はマップ指定が無くても、マップを選ばない限り表示しない（アプリと同じ）。
- Bot はアプリの `RAID_MAPS` と同じ一覧を持つ。一覧に無いマップ名が含まれていても 422 にはせず、そのマップだけを無視する（アプリと Bot の更新の時期がずれても送信が失敗しないように）。

### 4.5 送り方

- `PUT /api/share` の本文として、**圧縮しない JSON そのもの**を送る（`Content-Type: application/json`）。
- アプリの「送る内容を確認」は、同じ JSON を `eft_raidshare_YYYY-MM-DD.json` として保存する（何が送られるかを本人が確かめられるように）。
- 作成は `buildRaidShareData()`（`src/js/09-raid-share.js`・実装済み・Issue #31）。自動送信・今すぐ送信・JSON 保存で共通に使う。「送る内容を確認」ボタンは今は出撃準備タブの「進行タスク」見出しに仮置き（#32 で設定タブへ移す）。細かい作り方は `docs/出撃準備機能仕様書.md`「送る内容を確認」。
- 実装上の補足: マップ未指定の目標は `maps: []` のまま送る（クエストアイテムも同じ）。撃破の `detail` は距離 0 を書かない。カスタムタスクのアイテムは候補から選んだ本物のID（Issue #43）で、#43 より前に手入力で保存された仮アイテムID（`custom_item_…`）だけは `itemId` に入れない。

### 4.6 バージョンを上げるとき

- 項目の追加だけなら `v` は据え置く（Bot は知らないキーを無視する）。
- 意味や必須項目が変わるときは `v: 2` にする。Bot は対応していない版を受け取ったら 422 を返し、アプリは「アプリ（または Bot）を更新してください」と表示する。

## 7. ボードの画面構成

### 7.1 全マップ一覧（初期表示）

```
出撃ボード（PvP）  参加 4人: 🟥@A 🟦@B 🟩@C 🟨@D
──────────────────────────────
 1. Customs        🟥🟦🟩🟨  目標 12件（共通 3件）
 2. Interchange    🟥🟦🟩     目標  8件（共通 2件）
 3. Woods          🟦🟨       目標  5件
 ...
どのマップでもOKな目標: 9件（収集 6 / 撃破 3）
──────────────────────────────
[マップを選ぶ ▼] [参加する] [抜ける] [地図で見る] [終了]
最終更新 14:32 ・ 20:32 に自動終了（操作があれば延長）
```

**並び順（行き先選びのスコア）**
1. そのマップに**未チェックの固有目標**がある参加者の数（多い順）
2. 共通目標の数（多い順）
3. 未チェックの固有目標の合計数（多い順）

「どのマップでもOK」の目標はどのマップでも同じなので、並び順には使わず、下にまとめて件数だけ出す。

### 7.2 マップ表示

```
Customs（参加 4人）                          [全マップに戻る]
── 共通の目標 ──────────────────
★ 撃破 Scav ×5               🟥 あと5  🟦 あと3  🟩 あと5
★ 収集 ガス分析器 FIR ×2      🟥 あと1  🟨 あと2
★ タスク「Debut」             🟥🟦
── 撃破 ──
 PMC ×3 (head)                 🟩 あと3
── 収集・持ち込み ──
 ...
── 設置・調査・脱出 ──
 ...
── どのマップでもOK ──
 ...
```

- **共通の目標**（2人以上が重なる目標）を最上部に強調表示し、参加者の色マーカーと各自の残りを並べる。メンション（`<@id>`）も並べられる（embed 内のメンションは通知が飛ばない）。
- 撃破はパーティーで共有されるので、上の例では Scav を5体倒せば3人とも終わる（§8.1）。
- チェック済み（`done:true`）の目標は表示しない。全員がチェックした共通目標は消える。
- 表示名は、**最初にその目標を共有した人の `label`** を使う（言語が違っても合算はキーで行う）。

### 7.3 Discord の文字数制限への対応

- 1メッセージの embed は合計6000字、本文（description）は4096字、フィールドは25個まで。
- あふれる場合は、優先度の低い順（どのマップでもOK → 設置・調査・脱出 → 収集・持ち込み）に「…ほか N件」とまとめて省略する。共通の目標は省略しない。
- 全部を見たいときはアプリの仲間のボード（§11.4）で見る（文字数の制限が無い）。

### 7.4 色マーカー

- 参加順に `🟥 🟦 🟩 🟨 🟪` を割り当てる（5人まで）。
- 抜けた人の色は空きになり、次に参加した人が使う。
- アプリの仲間のボードでも同じ色の割り当てを使う。

## 8. 合算ロジック

対象マップの目標 = `maps` にそのマップを含む目標 ＋ `maps` が空の目標（設置を除く）。そのうち `done:false` のものだけを扱う。

Bot（Discord のボード）とアプリ（仲間のボード）は、この節の同じルールで合算する。

### 8.1 「同じ目標」とみなすキーと数の扱い

| cat | キー | 数の扱い |
|---|---|---|
| `bring` / `collect`（アイテム） | `cat` + `itemId` + `fir` | 各自の残りを並べる（アイテムは人ごとに必要） |
| `bring` / `collect`（カテゴリ指定） | `cat` + `categoryName` + `fir` | 各自の残りを並べる |
| `collect`（クエストアイテム） | 目標 `id` | 人ごと（クエストアイテムは各自で拾う） |
| `kill` | `label` + `detail` + 固有／どこでも | 各自の残りを並べる。**合計しない**（キルはパーティーで共有されるので、残りが一番多い人の数を倒せば全員が終わる） |
| `place` / `extract` / `locate` | 目標 `id` | 人ごと |

- 撃破は、マップ固有の目標と「どこでも」の目標をキーで分ける（「Customs で Scav」と「どこでも Scav」は別の目標として数えるため）。
- 目標 `id` は JSON API フォールバック中も API 本来の ID（24桁hex）で、言語や GraphQL 復旧の前後で変わらない（2026-11-11・Issue #45 で、`id` が訳文になっていた不具合を修正）。
- `custom:true` のタスクの目標は ID がアプリ内でしか通用しないので、`id` での突き合わせはしない（アイテム・撃破のキーは使える）。

### 8.2 共通タスク

- 同じタスクID（`custom:false`）を2人以上が持っていれば「同じタスクを進めている」として、共通の目標欄に出す。

### 8.3 共通目標

- キーが同じ目標を2人以上が持っていれば共通目標とする。

## 11. 連携と自動送信

流れはシーケンス図（冒頭のリンク）の 01〜03・06 を参照。

### 11.1 連携の流れ

**基本（6桁コード・`file://` でも GitHub Pages 版でも可）**
1. Discord で `/raid link` → 本人にだけ見えるメッセージで**6桁の連携コード**（5分で失効・1回限り）が届く
2. アプリの設定タブ「Discord 連携」に **Bot の URL** と連携コードを入力する
3. アプリが `POST /api/link { code }` を送る → Bot が**連携トークン**を発行 → アプリは localStorage に保存する
4. Bot は `/raid link` の返答を「連携が完了しました」に書き換える（返答の編集は15分以内に限られるため、それを過ぎたら書き換えない）
5. コードの入力間違いが続いたら、一時的に受け付けを止める（総当たり対策。送信元ごとと全体の両方に上限・§11.3）

**補助（「アプリの設定を開く」ボタン・GitHub Pages 版のみ）**
- 同じメッセージに「アプリの設定を開く」ボタン（`https://aiuhehe.github.io/eft-companion/#status`・設定タブを開くだけ）を付ける。**リンクにはコードも Bot の URL も入れない**。開いた先で、メッセージに出ている Bot の URL とコードを入力する（手順は基本と同じ）。
- 当初はハッシュ部にコードと Bot の URL を入れ（`#link=<6桁>&bot=<URL>`）、開いたら確認して連携する予定だった。そのリンクを開いた Chrome でセーフブラウジングに「危険なサイト」（フィッシング）と判定され、アプリのサイト全体が赤い警告画面になったためやめた（2026-11-12。そのブラウザのプロファイルだけで、Google の公開リストには載っていない）。「秘密のコード」と「別のサイトの URL」が入ったリンクを開いて「連携しますか？」と聞く流れが、フィッシングと同じ形になるため。

**解除**: `/raid unlink`（そのユーザーの全トークンを無効化）か、アプリの「連携解除」（`DELETE /api/link`）。

**アプリ側の保存先**: グローバルキー `eft_discord_link_v1`（Bot の URL・トークン・同期オン/オフ・最終同期時刻）。Discord のユーザーはモードをまたいで同じなのでモード別にはしない。送る中身は現在のモードのもの。全データバックアップには含めない（§3.1）。

### 11.2 自動送信

- アプリの設定「Discord に同期」が**オン**のときだけ送る（**初期状態はオフ**）。公開アプリなので、Bot を使っていない利用者からは何も送られない。
- 進行タスク・目標チェック・タスク完了が変わったら、**最後の変更から30秒待ってまとめて** `PUT /api/share` を送る。前回送った内容と同じなら送らない。
- 「**今すぐ送信**」ボタンで、30秒待たずに送れる（出撃直前用）。
- 本文は `buildRaidShareData()` の結果そのもの（圧縮しない JSON）。
- Bot は `shares` を書き換え、その人が参加中のボードを編集して更新する。
- アプリは設定タブと出撃準備タブに「14:32 に同期」と最終同期時刻を出す。
- 送信のタイミングは上の2つ（変更から30秒後の自動送信・今すぐ送信）だけ。どちらも結果は `PUT /api/share` の応答で分かり、アプリは次のように動く。メッセージは設定タブと出撃準備タブの同期状態の欄（最終同期時刻の横）に出し、次に送信が成功したら消す。
  - 204（成功）→ 最終同期時刻を更新する
  - 401（トークン無効・解除済み）→ 同期をオフにして「連携が解除されています」と出す
  - 413 / 422（大きすぎる・形式違い・対応していない `v`）→ 同期はオンのまま「アプリ（または Bot）を更新してください」と出す。アプリと Bot の一方だけが新しい形式に更新された場合に起きる。中身が変わるまで同じ内容は送り直さない（前回と同じ内容は送らないため、失敗を繰り返さない）
  - 429（送りすぎ）→ 応答の `Retry-After` の秒数だけ待ってから送り直す
  - 通信できない（Bot が止まっている・オフライン）→ 「同期できませんでした」と出し、次の変更か今すぐ送信のときにもう一度送る

### 11.3 API

| メソッド・パス | 認証 | 内容 | 主な応答 |
|---|---|---|---|
| `POST /api/link` | 本文の連携コード `{ code: "123456" }` | トークン発行 | 200 `{ token, userName }` / 400 `{ error: "invalid_code" }`（コード違い・使用済み・6桁の数字でない）・`{ error: "expired_code" }` / 429 `{ error: "too_many_attempts" }` 試行回数超過 |
| `DELETE /api/link` | `Authorization: Bearer <token>` | このトークンを無効化 | 204 |
| `PUT /api/share` | `Authorization: Bearer <token>` | 共有データを登録・更新 | 204 / 401 トークン無効 / 413 大きすぎる / 422 形式違い・未対応の `v` / 429 送りすぎ |
| `GET /api/boards` | `Authorization: Bearer <token>` | 自分が参加中のボード一覧（§11.4） | 200 / 401 |
| `GET /api/boards/:id` | `Authorization: Bearer <token>` | ボードの中身（§11.4） | 200 / 401 / 403 参加していない / 404 終了済み |
| `GET /api/guilds` | `Authorization: Bearer <token>` | ピンの共有先に選べるサーバーの一覧（§11.5） | 200 / 401 |
| `GET /api/guilds/:gid/pins?since=` | `Authorization: Bearer <token>` | ピンと登録タスク品（`since` 以降の変更分・削除を含む） | 200 / 401 / 403 メンバーでない |
| `PUT /api/guilds/:gid/pins/:id` | `Authorization: Bearer <token>` | ピンの追加・更新 | 200 / 401 / 403 / 422 |
| `DELETE /api/guilds/:gid/pins/:id` | `Authorization: Bearer <token>` | ピンの削除（30日間は元に戻せる） | 204 / 401 / 403 |
| `PUT /api/guilds/:gid/items/:id` | `Authorization: Bearer <token>` | 登録タスク品の追加・更新 | 200 / 401 / 403 / 422 |
| `PUT` / `GET /api/guilds/:gid/images/:id` | `Authorization: Bearer <token>` | ピンのメモ画像の保存・取得（JPEG・1枚1MBまで） | 200・204 / 401 / 403 / 413 |

**通信のきまり**
- **CORS**: 送信元では制限しない（`Access-Control-Allow-Origin: *`。`file://` の `null` も含む）。Cookie は使わず、認証はヘッダーの連携トークンだけなので、送信元を問わなくても安全性は落ちない。プリフライト（`OPTIONS`）では `Authorization` と `Content-Type` ヘッダーを許可する。
- 送信頻度の上限（Bot 側の保護）: `PUT /api/share` は1ユーザー1分に6回まで。超えたら 429 と `Retry-After` を返す。アプリは最後の変更から30秒待ってまとめて送るので、普通に使っていればこの上限には届かない。届くのは「今すぐ送信」を連打したときや、不具合でアプリが送り続けたときだけ（D1 の書き込み回数と Discord のメッセージ編集を守るための上限）。
- 連携コードの試行回数の上限（総当たり対策）: `POST /api/link` は送信元ごとに10分で10回、全体（送信元を問わない）で10分で50回まで。超えたら正しいコードでも 429 と `Retry-After`（窓の残り秒数）を返す。アプリは `Retry-After` の秒数を「しばらく待ってからもう一度お試しください（約N分）」のように出す。6桁の数字でない入力は数えない（アプリ側で全角数字・空白を整えてから送る）。
- 本文の上限: 1MB（§12）。

**連携トークンの扱い**
- トークンは `crypto.getRandomValues` で作る**32バイトの乱数**（base64url）。
- D1 にはトークンそのものではなく、**SHA-256 のハッシュだけを保存する**。トークンは人が決めるパスワードと違って推測できない長さの乱数なので、ソルトや bcrypt は使わず SHA-256 で十分。D1 の中身が漏れても、ハッシュからトークンは復元できず、なりすましには使えない。
- 照合のしかた: リクエストのたびに、受け取ったトークンを SHA-256 にして `links.token_hash` と一致するかを確かめる。Bot はトークンの控えを持たない。
- トークンそのものを持つのは本人のブラウザの localStorage だけ（Bot は発行時に1回だけ返す）。漏れたら `/raid unlink` で全トークンを無効にできる。
- トークンは URL に載せない（ヘッダーで送る）。
- トークンで出来るのは「本人の共有データの送信」「本人が参加中のボードを読む」「本人が在籍するサーバーのピンを読み書きする」ことだけ。Discord のアカウントそのものの権限は持たない。

### 11.4 仲間のボード（Bot が仲介）

アプリ同士は直接つながらないので、**Bot が仲介役**になる。各自のアプリが Bot に送った共有データを、同じボードの参加者のアプリが Bot から読み込む。

```
[Aのアプリ] ──PUT /api/share──▶ [Bot（Worker）+ D1] ◀──GET /api/boards/:id── [Bのアプリ]
                                        │
                                        └─ Discord のボード（要約）を編集
```

**入り方**
- ボードの **[地図で見る]** ボタン（リンクボタン）から開く。リンク先は GitHub Pages 版のアプリで、ハッシュ部にボード ID を入れる（`#board=<id>`）。ボード ID は秘密ではない（読み込みには連携トークンと参加が必要）。
- `file://` で使っている人は、出撃準備タブで参加中のボードを選ぶ（`GET /api/boards`）。

**読み込み API**
- `GET /api/boards` → 自分が参加中のボード一覧 `[{ id, guildName, channelName, gameMode, mode, selectedMap, memberCount, lastActivityAt }]`
- `GET /api/boards/:id` → `{ board: { id, gameMode, mode, selectedMap, lastActivityAt, expiresAt }, members: [{ userId, displayName, avatarUrl, colorIdx, syncedAt, share }] }`
  - `share` は §4 の共有データ（Bot で検証・整形済みのもの）。合算はアプリ側で行う（アプリはアイテムアイコンなどの API データを持っているので、Discord より見やすく出せる）。
  - **そのボードに参加している人だけ**が読める（参加していなければ 403）。中身はボードに出ているものと同じ範囲（目標のみ）。
- 出撃準備タブで仲間のボードを表示している間だけ、30秒ごとに再読み込みする。

**画面（出撃準備タブの中）**
- 参加中のボードを選ぶと、出撃準備タブの目標一覧に仲間の目標が重なる。行ごとに誰の目標かを**メンバー別の色**で示す（色はボードの参加順で、Discord と同じ）。
- 並び・まとめ方は Discord のボードと同じ（§7・§8）。文字数の制限が無いので、省略せずに全部出す。
- マップを選ぶと、アプリのマップ画像も表示する。ピンの共有先がそのボードのサーバーなら、サーバーのピン（§11.5）も同じ地図に出る。

### 11.5 マップピンの共有

マップタブのピン（目標の位置・メモ・必要な鍵・メモ画像）を、**Discord サーバー単位で Bot に持たせ、そのサーバーのメンバー全員で1セットを共有する**。ピンはゲーム内の位置という全員に共通の事実なので、各自のブラウザで別々に登録し直す必要をなくす。

**共有先のサーバー**
- アプリの設定タブ「Discord 連携」で、ピンの共有先を1つ選ぶ（`GET /api/guilds`）。候補は、本人がそのサーバーで `/raid` コマンドかボードのボタンを使ったことのあるサーバー（Bot は操作のたびに `guild_members` を記録する）。
- 共有先を選んでいないとき（連携していない利用者を含む）は、今までどおり各自のブラウザのピン（`eft_task_pins_v1`）だけを使う。

**誰が何をできるか**
- **そのサーバーのメンバーなら誰でも**、ピンと登録タスク品を追加・編集・削除できる。管理者だけに限る操作は設けない。
- メンバーかどうかは Discord に問い合わせて確かめる（REST の「サーバーメンバーの取得」。特権 Intent は不要）。結果は10分間 `guild_members.verified_at` に控え、サーバーを抜けた人はその後の読み書きができなくなる。
- 編集はピン単位で**後から保存したほうが残る**。ピンには最後に編集した人と日時を持たせ、アプリのピン詳細に「最終編集 @名前 11/11 14:32」と出す。
- 削除したピンは30日間残し、アプリの「最近削除したピン」から元に戻せる（誰でも編集できる代わりに、誤操作を取り消せるようにする）。30日を過ぎたら Cron で消し、メモ画像も R2 から消す。

**座標**
- API とデータベースでは、ピンの座標を**アプリ標準のマップ画像（`eft_maps_v1` の幅・高さ）に対する比率（0〜1）**で持つ。アプリは送るときに `x / width` に、受け取ったときに `x × width` に変換する。
- 各自がマップ画像を差し替えていても、サーバーのマップ画像（§6.3）を使っていても、同じ範囲の画像であれば位置は変わらない。

**同期のしかた**
- サーバーのピンは、アプリでは個人のピンとは別のグローバルキー `eft_task_pins_shared_v1`・`eft_custom_items_shared_v1` に控えとして持つ。個人のピン（`eft_task_pins_v1`）は消さないので、共有をやめれば元のピンに戻る。
- 読み込み: マップタブか出撃準備タブを開いたとき、表示している間は5分ごと、自分が編集した直後に `GET /api/guilds/:gid/pins?since=<前回の時刻>` で変更分だけを取得する。
- 書き込み: 追加・編集・削除はまず控えに反映して画面に出し、すぐに `PUT` / `DELETE` を送る。送れなかった変更は送信待ちとして残し、次の読み込みのときに送り直す（通信できない間もピンの登録は続けられる）。
- メモ画像: ピンの登録時に、アプリで縮小済みの JPEG（長辺1280px）を `PUT /api/guilds/:gid/images/:id` で R2 に保存する。表示時は連携トークン付きで取得し、IndexedDB（`eft_media`）にキャッシュする。
- 初めて共有先を選んだとき、個人のピンがあれば「今あるピン N件をこのサーバーに追加しますか？」と確認する。追加する場合、同じ目標の近く（比率で 0.01 以内）にすでにピンがあればそのピンは追加しない。

## 12. 受け取ったデータの検証（安全対策）

- 本文の大きさ: 1MB を超えたら 413。
- 形式チェック: `v`・`app`・必須項目・型・`cat` の値。超えたら 422。
- 件数と長さの上限は、**全タスクを進行中にしても収まる**ように実データから決める。不正なデータや壊れたデータで D1 と Discord のボードが埋まらないための上限で、普通の使い方を制限するものではない。

| 項目 | 上限 | 根拠（2026-11-10 の json.tarkov.dev で実測） |
|---|---|---|
| タスク数 | 1000件 | 全タスク数は regular 503件・pve 499件・pvp-season 462件。カスタムタスクとタスク追加の余裕を見て約2倍 |
| 1タスクの目標数 | 100件 | 最多は Collector の44件（99%のタスクは11件以下）。約2倍 |
| 文字列の長さ | 500字 | 最長はタスク名48字・目標の説明文129字（英語）/ 127字（日本語）。約4倍 |
| 本文の大きさ | 1MB | 全タスク・全目標（1416件）を進行中にした場合で約340KB。約3倍。D1 の1行の上限（2MB）にも収まる |
- ピンの上限: 1サーバーのピン5000件・登録タスク品500件・1ピンのメモ画像10枚・メモ500字・座標は 0〜1。メモ画像は JPEG のみ・1枚1MBまで（アプリの縮小後は数百 KB）。マップ名は `RAID_MAPS` の名前だけを受け付ける。
- **表示名はそのまま出さない**: Discord のマークダウン記号をエスケープし、`@everyone` / `@here` / `<@…>` などのメンションになる文字列を無効化する。メッセージ送信時は `allowed_mentions` で通知先を制限する。
- 知らないキーは捨ててから保存する。

## 14. Issue #9 の初期案からの変更点

Issue #9 の初期案は、出撃準備タブで共有コード（`EFTRS1:…`）をコピーし、Discord のコマンドに貼り付ける方式だった。Discord の入力欄の文字数制限（スラッシュコマンドの引数 6000字・モーダル 4000字）では目標一覧が収まらないため、最初からトークンで連携して自動送信する方式に変えた。

| 項目 | Issue #9 の初期案 | この設計書 |
|---|---|---|
| 共有の方式 | 出撃準備タブで共有コードをコピー（`EFTRS1:`・deflate＋base64url） | **設定タブで Bot と連携し自動送信**。共有コードと圧縮は廃止 |
| UI の場所 | 出撃準備タブのマップ選択の下 | **設定タブ「Discord 連携」**（Bot の URL・連携コード入力・同期オン/オフ・今すぐ送信・最終同期時刻・連携解除・送る内容を確認）。出撃準備タブには同期状態と仲間のボード |
